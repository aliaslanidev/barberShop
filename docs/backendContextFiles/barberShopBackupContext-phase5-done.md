# barberShopBackupContext.md

> این فایل، مرجع کامل وضعیت پروژه‌ست. هر چت جدیدی که با Claude درباره‌ی این
> پروژه باز می‌شه، باید این فایل رو بخونه تا بفهمه داستان از چه قراره.
> هر مرحله از نقشه‌راه فقط وقتی تیک می‌خوره که کاربر (صاحب پروژه) تست کرده و
> تایید کرده که کار می‌کنه. تا اون موقع `[ ]` می‌مونه.

آخرین به‌روزرسانی: فاز ۵ تمام شد ✅ (طبق اعلام کاربر) — سیستم مرخصی (`LeaveRequest` + `TimeOff`)، تعطیلات، تنظیمات سالن، و بازطراحی کامل پرمیشن‌های آرایشگر (`customPrice`، `isActive`، `viewCustomers`، `BlockedSlot`، `workingDays`). بعد از فاز ۵ این موارد اضافه شد و **هنوز نیاز به تست و تایید کاربر دارن** (جزئیات پایین، آخر بخش فاز ۵): (الف) نگه‌داری موقت اسلات (`SlotHold`)، (ب) اصلاحات قبل از فاز ۶: هدر سایت با وضعیت لاگین، قیمت هر آرایشگر تو فلوی رزرو، صفحه‌ی پیش‌فاکتور/اطلاعیه بعد از رزرو، نمایش همه‌ی نوبت‌ها برای آرایشگر، و ذخیره‌ی قیمت تو خود نوبت (`Booking.price`). قبل از تست باید دو مایگریشن اجرا بشه: `npx prisma migrate dev --name add_slot_holds` و `npx prisma migrate dev --name add_booking_price`. بعد از تایید این‌ها، آماده‌ی شروع فاز ۶.

## ⚠️ نکته‌ی حیاتی درباره‌ی سبک همکاری

**صاحب پروژه قصد یادگیری کدنویسی نداره.** هدف صرفاً راه‌اندازی و تحویل
پروژه‌ی کارکرده‌ست، نه آموزش. یعنی تو هر چت بعدی:
- Claude باید کارها رو مستقیماً خودش انجام بده (نوشتن فایل‌ها، اجرای
  دستورات لازم در sandbox، دادن دستورات آماده‌ی کپی‌پیست برای چیزهایی که
  فقط روی سیستم خودِ کاربر قابل اجراست مثل `npm install` یا ست‌کردن دیتابیس).
- به‌جای توضیح مفهومی طولانی یا آموزش «چرا این‌جوری»، باید نتیجه/فایل
  نهایی رو تحویل بده و فقط در حد لازم خلاصه توضیح بده.
- سوال بپرس فقط وقتی تصمیمی معماری/محصولی لازمه که Claude نمی‌تونه خودش
  حدس بزنه؛ در غیر این صورت با بهترین‌ practice پیش بره و ادامه بده.

## ۱. معرفی کلی پروژه

سایت رزرو نوبت یک **آرایشگاه مردانه**، کاملاً **فارسی** (RTL)، با نسخه‌ی
**PWA** (قابل نصب روی گوشی). فرانت تقریباً تکمیله. بک‌اند از صفر داریم
می‌سازیم و قراره جایگزین لایه‌ی mock فعلی (`lib/data/*.ts`) بشه.

## ۲. استک فنی

| بخش | تکنولوژی |
|---|---|
| فرانت | Next.js 14 (App Router)، TypeScript، Tailwind، shadcn/radix-ui، react-hook-form + zod، react-multi-date-picker (تقویم جلالی) |
| بک‌اند | Node.js + **Express** + **Prisma ORM** (TypeScript) |
| دیتابیس | **PostgreSQL** |
| احراز هویت | JWT (Bearer token)، bcrypt برای هش پسورد |
| نوتیفیکیشن | **Web Push API** استاندارد (پکیج `web-push`, رایگان، بدون سرویس ثالث) + جدول Notification برای inbox داخل پنل |
| محل بک‌اند | پوشه‌ی `server/` **داخل همین ریپو** (نه ریپوی جدا)، پکیج جدا از فرانت |

### چرا این تصمیم‌ها؟
- Express + Prisma: ساده‌تر از NestJS برای یادگیری و شروع سریع، مستندات و جامعه‌ی بزرگ.
- `server/` داخل همون ریپو: مدیریت راحت‌تر برای توسعه‌ی تک‌نفره، در آینده به‌راحتی قابل جداشدنه.
- Web Push به‌جای Firebase/OneSignal: کاملاً رایگانه و چون PWA از قبل service worker داره، اضافه‌کردنش هزینه‌ی فنی کمی داره.

⚠️ نکته: یک‌بار تو چت «با nest نوشته شده» گفته شد. **فرض شده منظور Next.js
بوده** (نه فریم‌ورک NestJS) چون کل ساختار آپلودشده Next.js App Router است.
اگه اشتباهه، باید بک‌اند از Express به NestJS تغییر کنه — **این هنوز به‌صورت
صریح توسط کاربر تایید نشده، باید مرحله اول تایید بشه.**

## ۵. نقش‌ها و سطح دسترسی

### قانون ثبت‌نام و مدیریت نقش‌ها (مهم)
- **ثبت‌نام عمومی (فرم register) همیشه و فقط نقش `CUSTOMER` می‌سازه.**
  هیچ راهی برای اینکه یک کاربر با ثبت‌نام خودش آرایشگر/مدیر/ادمین بشه وجود نداره.
- نقش‌های `BARBER`, `MANAGER`, `ADMIN` **فقط توسط ادمین** ساخته می‌شن
  (از پنل ادمین، مثل همون `createBarber` که در `barbers.ts` هست).
- برای این نقش‌ها (`BARBER`, `MANAGER`)، **موبایل (یوزرنیم) و پسورد رو
  خودِ ادمین موقع ساخت تعیین می‌کنه**، و خودِ اون کاربر (آرایشگر/مدیر سالن)
  **اجازه‌ی تغییر یوزرنیم یا پسورد خودش رو نداره** — فقط ادمین می‌تونه
  این اطلاعات رو ویرایش/ریست کنه. یعنی نباید هیچ endpoint
  «تغییر پسورد خودم» برای نقش آرایشگر/مدیر سالن وجود داشته باشه؛ فقط
  ادمین (endpoint `updateBarber`) می‌تونه mobile/password رو عوض کنه.
  (این قانون شامل خودِ ادمین نمی‌شه — ادمین می‌تونه پسورد خودش رو عوض کنه،
  چون صفحه‌ی admin/settings همین قابلیت رو داره.)

### مشتری (Customer)
- **تنها رولی که از مسیر عمومی `register` ساخته می‌شه.** هر ثبت‌نامی، فارغ
  از هر چیزی، رول `CUSTOMER` می‌گیره. هیچ فرم ثبت‌نام دیگه‌ای برای رول‌های
  دیگه وجود نداره/نباید وجود داشته باشه.
- مشتری آزاده رمز عبور خودش رو تغییر بده (چون خودش با اون ثبت‌نام کرده).
- دیدن صفحه اصلی، رزرو نوبت با دو مسیر ورودی:
  1. **اول آرایشگر** → دیدن خدماتی که همون آرایشگر انجام می‌ده → انتخاب سرویس
  2. **اول سرویس** → دیدن آرایشگرهایی که اون سرویس رو انجام می‌دن → انتخاب آرایشگر
  - بعد: انتخاب تاریخ (جلالی) + ساعت + توضیحات → ثبت نهایی
- صفحه‌ی شخصی: دیدن/ویرایش پروفایل، نوبت‌های فعلی و تاریخچه
- بعد از اتمام سرویس: می‌تونه امتیاز (۱ تا ۵) + نظر برای آرایشگر ثبت کنه.
  **امتیازها عمومی هستن** — همه (حتی قبل از رزرو) می‌تونن ببینن.

### آرایشگر (Barber)
- **نمی‌تونه خودش با رول آرایشگر ثبت‌نام کنه.** حساب آرایشگر فقط توسط ادمین
  از پنل ساخته می‌شه (`admin/barbers` → افزودن آرایشگر) و ادمین همون لحظه
  موبایل (username) و پسورد اولیه رو تعیین می‌کنه.
- آرایشگر **حق تغییر موبایل یا پسورد خودش رو نداره** — این‌ها فقط از طریق
  ادمین قابل تغییرن. تو صفحه‌ی پروفایل/تنظیمات آرایشگر نباید فرم تغییر
  رمز/موبایل وجود داشته باشه.
- پنل شخصی خودش، فقط نوبت‌ها و مشتری‌های **خودش** رو می‌بینه (هیچ‌وقت
  مشتری‌ها/نوبت‌های آرایشگر دیگه رو نمی‌بینه).
- پرمیشن‌های اختیاری (هرکدوم رو ادمین جدا فعال/غیرفعال می‌کنه، هیچ پیش‌فرض
  خودکاری بر اساس «نوع آرایشگر» وجود نداره) — **تعریف نهایی بعد از بازطراحی فاز ۵**:
  - `manageServices` — آرایشگر می‌تونه یکی از خدمات **اختصاص‌داده‌شده توسط ادمین**
    رو موقتاً فعال/غیرفعال کنه (فیلد `isActive` روی `BarberService`، پیش‌فرض true).
    کاتالوگ سراسری خدمات همچنان فقط دست ادمینه.
  - `managePricing` — تعیین قیمت خودش برای هر سرویس (فیلد nullable `customPrice`
    روی `BarberService`؛ اگه null باشه از `Service.priceValue` استفاده می‌شه)
  - `manageSchedule` — انتخاب روزهای هفته‌ای که کار می‌کنه (فیلد `workingDays Weekday[]`
    روی `BarberProfile`؛ آرایه‌ی خالی = تابع روزهای باز سالن). **ساعات کاری ثابت و
    سراسری سالنه (۹ تا ۲۱)**، آرایشگر ساعت شخصی نداره.
  - `manageTimeOff` — ثبت مستقیم مرخصی یک‌روزه بدون تایید (بدونش: `LeaveRequest` با
    وضعیت PENDING ساخته می‌شه)
  - `blockSlots` — بستن ساعت خاص تو یه روز (مدل `BlockedSlot`)، ریزتر از مرخصی تمام‌روز
  - `cancelOwnBookings` — لغو نوبت‌های تاییدشده‌ی خودش
  - `viewCustomers` — دیدن لیست مشتری‌های خودش (**جدید؛ قبلاً همیشه فعال بود**)
- پرمیشن‌های ثابت (به همه آرایشگرها خودکار تعلق می‌گیره): دیدن داشبورد خودش،
  نوبت‌های خودش، تاریخچه‌ی خودش، شروع/پایان سرویس، و **ثبت مرخصی** (فرقش فقط
  اینه که مستقیم ثبت می‌شه یا به صورت درخواست).
- **شروع/پایان کار**: روی خودِ `Booking` انجام می‌شه —
  `CONFIRMED → IN_PROGRESS → COMPLETED` (نه یه مفهوم جدا مثل «شیفت روزانه»). ✅ قطعی

### مدیر سالن (Manager) — پرمیشن قطعی شد ✅
- تصمیم شد: **زیرمجموعه‌ی دسترسی ادمین، یک سالن (نه چندسالنی)**.
- مثل آرایشگر، **فقط ادمین** حساب مدیر سالن رو می‌سازه و username/password
  رو تعیین می‌کنه؛ مدیر سالن هم حق تغییر خودشون رو نداره.
- دسترسی‌هاش: دیدن همه‌ی نوبت‌ها، گزارش‌ها، لیست آرایشگرها + تایید/رد
  درخواست مرخصی (`LeaveRequest`).
- **ندارد**: ساخت/حذف آرایشگر، تغییر پرمیشن‌های آرایشگر، دسترسی به
  تنظیمات کلی سالن (قیمت پیش‌فرض، ساعات کاری کلی، اطلاعات تماس سالن).

### ادمین (Admin)
- بالاترین سطح دسترسی، به همه‌چیز.
- **تنها نقشی که مجاز به ساختن حساب برای بقیه‌ی رول‌ها (آرایشگر، مدیر
  سالن، حتی ادمین دیگه) هست** — و در همون لحظه‌ی ساخت، username/password
  رو خودش تعیین می‌کنه.
- اضافه‌کردن آرایشگر + تعیین دقیق پرمیشن‌های هرکدوم.
- تایید/رد درخواست مرخصیِ آرایشگرهایی که پرمیشن `manageTimeOff` رو ندارن —
  از طریق مدل `LeaveRequest` (pending/approved/rejected)، جدای جدول نهایی
  `TimeOff`. ✅ قطعی — مدیر سالن هم می‌تونه همین کار رو انجام بده.
- تعیین قیمت پیش‌فرض سالن (آرایشگرهای بدون `managePricing` از همین استفاده می‌کنن).
- تعیین روزهای تعطیلی سالن.

## ۶. جریان‌های کلیدی کسب‌وکار

1. **رزرو نوبت** — دو مسیر ورودی (بالا توضیح داده شد) → یک `Booking`
   با status اولیه‌ی `CONFIRMED` ساخته می‌شه.
2. **شروع/پایان سرویس** — آرایشگر روز رزرو، دکمه‌ی «شروع کار» می‌زنه
   (`IN_PROGRESS`)، بعد «پایان کار» (`COMPLETED`).
3. **امتیازدهی** — بعد از `COMPLETED`، مشتری امتیاز ۱ تا ۵ + نظر ثبت می‌کنه.
   معدل امتیاز + تعداد آرا رو تو پروفایل عمومی هر آرایشگر نشون می‌دیم.
4. **مرخصی** — آرایشگر بدون پرمیشن → درخواست می‌ده → صف انتظار ادمین →
   تایید/رد. آرایشگر با پرمیشن → مستقیم ثبت می‌شه، نیازی به تایید نیست.
5. **نوتیفیکیشن** — رویدادهایی که باید Push/inbox بفرستن (فهرست اولیه،
   قابل اضافه‌شدن):
   - تایید ثبت نوبت برای مشتری
   - یادآوری نزدیک‌شدن نوبت
   - شروع/پایان کار (به مشتری اطلاع بده کارش شروع/تموم شد)
   - تایید یا رد درخواست مرخصی (به آرایشگر)
   - درخواست مرخصی جدید (به ادمین)
   - نوبت جدید ثبت شد (به آرایشگر مربوطه)
   - لغو نوبت (به هردو طرف)

## ۱۰. نکات مهم برای Claude در چت‌های بعدی

- همیشه اول همین فایل رو مرجع بگیر، نه فرض‌های خودت.
- کدی که قبلاً نوشته شده رو (بخش ۴) تکرار نکن مگر کاربر بگه تغییرش بده.
- هیچ مرحله‌ای رو «تمام‌شده» فرض نکن مگر این فایل صراحتاً `[x]` داشته باشه.
- زبان پاسخ‌ها فارسی، و سبک کدنویسی/کامنت‌ها هم فارسی (مطابق کدهای فعلی پروژه).
- **کاربر قصد یادگیری برنامه‌نویسی نداره، فقط می‌خواد پروژه راه بیفته.**
  یعنی:
  - توضیح آموزشیِ اضافه (چرا فلان الگو، تفاوت X و Y و ...) نده مگر صراحتاً
    خواسته بشه؛ مستقیم برو سر اجرا و نتیجه.
  - تصمیم‌های فنی جزئی (اسم متغیر، ساختار داخلی فایل، جزئیات پیاده‌سازی)
    رو خودت بگیر و کار رو جلو ببر؛ فقط برای تصمیم‌های سطح‌بالا (که رو
    scope/dataیا رفتار کاربر تاثیر داره) سوال بپرس.
  - همیشه، تا جایی که ممکنه، به‌جای «این کارو بکن» خودت مستقیم انجامش بده.
- ثبت‌نام عمومی همیشه رول `CUSTOMER` می‌سازه؛ رول‌های دیگه فقط با ابزار
  ادمین (که هنوز پیاده نشده — بخشی از فاز ۳/۴) ساخته می‌شن، و
  username/password اون‌ها فقط از طریق ادمین قابل تغییره (نه خودشون).
- **فایل‌ها همیشه کامل تحویل داده بشن** (کل محتوای فایل، آماده‌ی کپی‌پیست)، نه
  diff یا «این خط رو اضافه کن». همراه هر فایل مسیر دقیقش تو پروژه گفته بشه
  (اسم فایل‌های دانلودی ممکنه مثل `page.tsx` تکراری باشن و قاطی بشن).
- **کار قدم‌به‌قدم**: کاربر می‌خواد مشکلات یکی‌یکی حل بشن («شمرده شمرده»)، نه
  همه با هم. حدس نزن؛ اگه فایلی لازمه، اسم/دستور پیداکردنش رو بگو (کاربر
  ویندوز/PowerShell داره — `grep` نیست، از `Get-ChildItem ... | Select-String`
  استفاده کن).
- فایل‌های واقعی کاربر رو قبل از تغییر بخون؛ اگه کاربر فایلی فرستاد که با
  نسخه‌ی تحویل‌داده‌شده‌ی قبلی فرق داره، یعنی هنوز جایگزین نکرده — نسخه‌ی خودش
  مبنای کار نیست، بهش بگو.

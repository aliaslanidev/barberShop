## ۰. تغییرات این نسخه نسبت به نسخه قبلی سند (مهم — بخوان اول)

تصمیم جدید در مدل کسب‌وکار آرایشگرها گرفته شده که **جایگزین بخش قبلی «Professional / Regular» می‌شود:**

- ❌ **حذف شد:** فیلد `barberType` (professional | regular) به‌عنوان یک دسته‌بندی از پیش تعریف‌شده که پرمیشن پیش‌فرض بهش وصل بود.
- ✅ **جایگزین شد با:** یک نقش سیستمی واحد `Barber` بدون هیچ زیرنوعی. **هر آرایشگر مجموعه پرمیشن‌های خودش را دارد که تک‌به‌تک توسط ادمین تعیین می‌شود** — نه بر اساس یک برچسب از پیش تعیین‌شده (professional/regular).
- یعنی مثلاً:
  - آرایشگر «X» می‌تونه پرمیشن‌های `manage_schedule` (تعیین تعطیلی/روزهای کاری)، `manage_time_off`، `manage_services` و `manage_pricing` رو داشته باشه.
  - آرایشگر «Y» می‌تونه هیچ‌کدوم از این پرمیشن‌ها رو نداشته باشه و فقط پرمیشن‌های پایه (دیدن نوبت‌های خودش، مشتریان خودش، شروع/پایان سرویس) رو داشته باشه.
  - این دو تا از نظر سیستم **هر دو فقط `role: barber` هستن** — هیچ فیلد نوع/دسته‌ای بینشون فرق نمی‌ذاره؛ تنها چیزی که فرق می‌کنه آرایه‌ی `permissions` هست.
- **چرا این تغییر مهمه:** در مدل قبلی، `barberType: professional` به‌نوعی القا می‌کرد که یک دسته‌ی از پیش تعریف‌شده از پرمیشن‌ها وجود داره (even اگر مستند تاکید می‌کرد پرمیشن‌ها دستی داده می‌شن). در مدل جدید هیچ مفهوم میانی‌ای بین «نقش» و «پرمیشن» وجود نداره — این باعث میشه منطق ساده‌تر، انعطاف‌پذیرتر و بدون ابهام بشه.
- این تغییر روی **مستندسازی اسکوپ** اعمال شده. کدی که تا الان نوشته شده (فاز ۳ و بخشی از فاز ۴) بر پایه مدل قدیم (`barberType`) ساخته شده و **باید رفکتور بشه** — جزئیات لازم برای رفکتور در بخش ۵ و ۶ این سند اومده.

## ۱. معرفی و چشم‌انداز پروژه

یک پلتفرم کامل مدیریت سالن آرایش/آرایشگاه مردانه و رزرو نوبت آنلاینه، نه صرفاً یه فرم رزرو ساده. شامل:

- سایت عمومی (لندینگ، خدمات، آرایشگرها، رزرو)
- ثبت‌نام/ورود مشتری
- رزرو نوبت با اسلات‌های زمانی ثابت یک‌ساعته
- پنل مشتری، پنل آرایشگر، پنل مدیر سالن (Salon Manager)، پنل ادمین
- سیستم نقش/پرمیشن گرانولار
- پشتیبانی PWA

**ایده‌ی کلیدی کسب‌وکار (به‌روزشده):** همه‌ی آرایشگرها یک نقش سیستمی واحد دارن (`Barber`). ادمین هر آرایشگر رو تعریف می‌کنه و مشخص می‌کنه **دقیقاً چه پرمیشن‌هایی** داره — مثلاً می‌تونه نوبت‌ها، تعطیلی‌های روزانه و بازه‌ی زمانی کاری خودش رو مدیریت کنه، یا قیمت‌ها و خدماتش رو خودش تعیین کنه. این استقلال، نقطه‌به‌نقطه (permission-by-permission) و کاملاً به تشخیص ادمینه — نه از روی یک دسته‌بندی از پیش تعریف‌شده.

## ۲. استک فنی واقعی (Actual Tech Stack)

> این استک با پروفایل عمومی فرانت‌اند من (React/MUI/Redux/TanStack Query) فرق داره — این پروژه مشخصاً روی این استک ساخته شده:

- **فریم‌ورک:** Next.js 14.2.5 (App Router)
- **زبان:** TypeScript
- **استایل:** Tailwind CSS
- **کامپوننت‌ها:** Radix UI primitives (dialog, label, popover, select) + کامپوننت‌های سبک shadcn/ui (در `components/ui/`)
- **فرم‌ها:** react-hook-form + zod + @hookform/resolvers
- **PWA:** @ducanh2912/next-pwa
- **فونت فارسی:** @fontsource/vazirmatn
- **تاریخ شمسی:** react-multi-date-picker
- **توست/نوتیفیکیشن UI:** sonner
- **آیکون:** lucide-react

**زبان/جهت:** فارسی، RTL، معماری برای پشتیبانی چندزبانه در آینده باز نگه داشته شده.

⚠️ **نکته‌ی مهم:** فعلاً هیچ بک‌اند واقعی (API/دیتابیس) وصل نیست. تمام داده‌ها (آرایشگرها، خدمات، سشن‌ها) در فایل‌های mock داخل `lib/data/` به‌صورت آرایه‌ی در-حافظه شبیه‌سازی شده‌ان. سند اسکوپ اولیه از FastAPI/PostgreSQL برای بک‌اند صحبت کرده بود، ولی این هنوز پیاده نشده.

## ۴. مدل نقش‌ها و پرمیشن‌ها (به‌روزشده — تغییر اصلی این نسخه)

**۴ نقش سیستمی:** Admin, Salon Manager, Barber, Customer

قانون کلیدی طراحی (فرمول جدید، ساده‌تر شده):

```
ROLE + PERMISSIONS
```

(دیگر `TYPE` بین این دو وجود ندارد.)

مثال جدید:

```
role = barber
permissions = [manage_services, manage_pricing, manage_schedule, manage_time_off]
```

در برابر:

```
role = barber
permissions = []   (یا فقط پرمیشن‌های پایه‌ی خودکار: view_own_dashboard, view_own_bookings, ...)
```

### شرح نقش‌ها

- **Admin:** دسترسی کامل به کل پلتفرم؛ تنها مرجع تغییر نقش/پرمیشن آرایشگر.
- **Salon Manager:** پرمیشن‌هاش رو ادمین تعریف می‌کنه؛ به‌صورت پیش‌فرض به بخش‌های حساس (نقش/پرمیشن/تنظیمات سیستم) دسترسی نداره مگر صراحتاً داده بشه. *(بدون تغییر نسبت به قبل)*
- **Barber (اصلاح‌شده):** یک نقش سیستمی واحد، **بدون هیچ زیرنوع/دسته‌بندی.** هر آرایشگر یک آرایه‌ی `permissions` مخصوص به خودش داره که ادمین تک‌به‌تک تعیین می‌کنه. هیچ مقدار پیش‌فرضی از یک «نوع» به آرایشگر پرمیشن اضافه نمی‌کنه.
- **Customer:** با ثبت‌نام عمومی خودکار ساخته می‌شه؛ نمی‌تونه نقش خودش رو بالا ببره. *(بدون تغییر)*

### پرمیشن‌های آرایشگر (لیست کامل — بدون تغییر نسبت به سند اصلی)

**پایه (معمولاً به همه آرایشگرها تعلق داره، صرف‌نظر از پرمیشن‌های اختیاری):**
- `view_own_dashboard`
- `view_own_bookings`
- `view_own_customers`
- `view_own_history`
- `start_service`
- `end_service`
- `view_service_history`

**اختیاری/قابل واگذاری (ادمین تک‌به‌تک به هر آرایشگر می‌ده یا نمی‌ده):**
- `manage_services` — انتخاب/تعیین خدماتی که ارائه می‌ده
- `manage_pricing` — تعیین قیمت خدمات خودش
- `manage_schedule` — تعیین روزهای کاری و بازه‌ی ساعت کاری خودش
- `manage_time_off` — ثبت مرخصی/تعطیلی روزانه‌ی خودش
- `block_slots` — بلاک کردن اسلات‌های زمانی مشخص
- `cancel_own_bookings` — کنسل کردن نوبت‌های تاییدشده‌ی خودش

قانون‌های سخت کسب‌وکار (بدون تغییر):
- اسلات‌های زمانی **globally fixed** (یک‌ساعته) — هیچ نقشی (حتی ادمین) نمی‌تونه اسلات دلخواه بسازه.
- Availability باید **سمت سرور** محاسبه بشه، نه فرانت‌اند.
- بلاک/کنسل کردن اسلاتی که نوبت تاییدشده داره، نباید نوبت رو بی‌صدا حذف کنه — باید فلو تایید/اطلاع‌رسانی جدا داشته باشه.

## ۵. چی ساخته شده (وضعیت فعلی، به تفکیک فاز)

### فاز ۳ — پنل آرایشگر (تکمیل‌شده، **ولی بر پایه‌ی مدل قدیمی `barberType` — نیاز به رفکتور**)
فایل‌های جدید:
- `lib/data/barber-session.ts` — شبیه‌سازی سشن با ثابت `CURRENT_BARBER_ID`
- `lib/data/barber-permissions.ts` — ⚠️ منطق فعلی احتمالاً پرمیشن رو بر اساس `barberType` مشتق می‌کنه؛ باید تغییر کنه به خواندن مستقیم آرایه‌ی `permissions` هر آرایشگر بدون واسطه‌ی type
- `lib/data/appointments.ts`
- `components/barber/barber-nav.tsx` — باید بر اساس پرمیشن نمایش داده بشه، نه بر اساس professional/regular
- `app/barber/layout.tsx`
- `app/barber/dashboard/page.tsx`
- `app/barber/bookings/page.tsx` (دکمه‌های شروع/پایان سرویس)
- `app/barber/customers/page.tsx`
- `app/barber/services/page.tsx` — چک دسترسی باید بشه `hasPermission('manage_services')`
- `app/barber/schedule/page.tsx` — چک دسترسی باید بشه `hasPermission('manage_schedule')`
- `app/barber/time-off/page.tsx` — چک دسترسی باید بشه `hasPermission('manage_time_off')`

**نحوه‌ی تست قدیمی (دیگر معتبر نیست):** قبلاً با `CURRENT_BARBER_ID = "ali"` (professional) منوهای خدمات/زمان‌بندی/مرخصی دیده می‌شد؛ با `"reza"` (regular) فقط داشبورد/نوبت‌های امروز/مشتریان من دیده می‌شد.

**نحوه‌ی تست جدید (باید این‌طور بشه):** با تغییر آرایه‌ی `permissions` در seed data برای هر `CURRENT_BARBER_ID`، منوهای مربوطه باید نمایش/مخفی بشن — مستقل از هر نوعی. مثلاً اگه به `"reza"` پرمیشن `manage_schedule` داده بشه، باید منوی «زمان‌بندی» رو ببینه، حتی بدون تغییر «نوع».

### اصلاحات سایت عمومی (تکمیل‌شده — بدون تغییر)
- مشکل: دکمه‌های «رزرو آنلاین نوبت» و «رزرو نوبت» در صفحه اصلی هیچ `href`/`Link`ی نداشتن (فقط تو هدر کار می‌کرد).
- رفع شد: در `app/(site)/page.tsx` هر دو دکمه به `/booking` لینک شدن.
- به `components/header.tsx` دکمه‌ی «صفحه اصلی» (`/`) و «ورود» (`/login`) اضافه شد.
- صفحه‌ی `app/(site)/login/page.tsx` ساخته شد: فرم شماره موبایل + رمز عبور با react-hook-form/zod، بدون اتصال واقعی به بک‌اند (کامنت `TODO` برای اتصال بعدی API گذاشته شده).
- `components/ui/input.tsx` (که وجود نداشت) اضافه شد.

### فاز ۴ — پنل ادمین (در حال شروع)
ساخته‌شده تا این لحظه:
- `lib/data/admin-session.ts` — شبیه‌سازی ادمین ثابت (`CURRENT_ADMIN`)، چون ادمین طبق مستند همیشه full-access داره و نیاز به چک permission ندارد (برخلاف آرایشگر)
- `components/admin/admin-nav.tsx` — نوار ناوبری با آیتم‌های: داشبورد، آرایشگرها، خدمات و قیمت، نوبت‌ها، تعطیلات، گزارش‌ها، تنظیمات
- `app/admin/layout.tsx` — چک نقش (اگر ادمین نباشد ریدایرکت به `/login`) + رندر AdminNav
- `app/admin/dashboard/page.tsx` — کارت‌های آماری (نوبت‌های امروز، آرایشگرهای فعال، خدمات فعال، درآمد ماه — همه mock)
- `lib/data/barbers.ts` **گسترش داده شد** (نه جایگزین): فایل قبلی که برای سایت عمومی/بوکینگ استفاده می‌شد (فیلدهای `bio`, `initials`, `serviceIds` و توابع `getBarberById`, `getBarbersByService`, `getServicesByBarber`) نگه داشته شد و این‌ها اضافه شدن:
  - فیلدهای `permissions`, `mobile`, `isActive`
  - ⚠️ فیلد `barberType` هم اضافه شده بود که طبق این نسخه سند **باید حذف بشه**
  - توابع مدیریتی: `getAllBarbers`, `createBarber`, `updateBarber`, `setBarberType` (⚠️ باید حذف بشه — دیگه مفهوم type نداریم)، `updateBarberPermissions`, `deleteBarber`
  - داده‌ی seed فعلی: ۴ آرایشگر — `ali` و `hamed` (تا الان professional)، `reza` و `mehdi` (تا الان regular) → باید به یک آرایه‌ی `permissions` مستقیم برای هرکدوم تبدیل بشه (بدون لیبل professional/regular)

**نحوه‌ی دسترسی به پنل ادمین در حالت فعلی:** چون سیستم لاگین واقعی وصل نیست، مستقیم برو به `/admin/dashboard` — `admin-session.ts` همیشه یک ادمین ثابت برمی‌گردونه، نیازی به لاگین یا تغییر مقدار (مثل `CURRENT_BARBER_ID`) نیست.

## ۶. کارهای رفکتور لازم برای اعمال مدل جدید (قبل از ادامه فاز ۴)

این‌ها باید قبل یا حین ساخت صفحه‌ی `/admin/barbers` انجام بشن:

1. **حذف فیلد `barberType`** از تایپ آرایشگر در `lib/data/barbers.ts` و از داده‌ی seed.
2. **حذف تابع `setBarberType`** و هر منطقی که پرمیشن پیش‌فرض رو بر اساس type محاسبه می‌کرد.
3. **اصلاح `lib/data/barber-permissions.ts`** — باید فقط از روی آرایه‌ی `permissions` هر آرایشگر (بدون واسطه‌ی type) پاسخ بده به سوال «آیا این آرایشگر پرمیشن X رو داره؟».
4. **اصلاح seed داده‌ی آرایشگرها** — هر ۴ آرایشگر (`ali`, `hamed`, `reza`, `mehdi`) باید آرایه‌ی `permissions` مستقل و صریح داشته باشن (نمونه‌ی پیشنهادی: `ali` و `hamed` همون پرمیشن‌های گسترده رو نگه دارن ولی به‌عنوان انتخاب صریح ادمین، نه به‌خاطر یک «نوع»؛ `reza` و `mehdi` می‌تونن پرمیشن کمتر یا صفر داشته باشن).
5. **اصلاح `components/barber/barber-nav.tsx`** — شرط نمایش هر آیتم منو باید `hasPermission('manage_services')` و مشابه باشه، نه چک `barberType === 'professional'`.
6. **اصلاح صفحات** `app/barber/services`, `app/barber/schedule`, `app/barber/time-off` — گارد دسترسی باید پرمیشن‌محور بشه.
7. طراحی UI صفحه‌ی آینده‌ی `/admin/barbers` باید به‌جای «تغییر نوع آرایشگر»، مستقیماً یک چک‌لیست/toggle از پرمیشن‌های قابل واگذاری رو برای هر آرایشگر نشون بده.

### فازهای بعدی (طبق سند اصلی، هنوز شروع نشده)
- **فاز ۵ — Service Tracking:** Start/End Service به‌صورت واقعی (الان فقط UI آرایشگر داره، بدون بک‌اند)، وضعیت Completed
- **فاز ۶ — Reviews:** امتیاز/نظر مشتری، خلاصه‌ی امتیاز آرایشگر
- **فاز ۷ — Notifications:** PWA Push، تنظیمات نوتیفیکیشن، نوتیفیکیشن رویدادمحور
- **فاز ۸ — Advanced Integrations:** واتس‌اپ، پیامک، گزارش‌گیری پیشرفته

### بک‌اند (هنوز اصلاً شروع نشده)
- هیچ API واقعی وصل نیست؛ همه‌چیز mock در `lib/data/` است.
- سند اولیه FastAPI + PostgreSQL رو پیشنهاد داده بود.
- Availability Engine (محاسبه‌ی اسلات‌های آزاد بر اساس ساعات کاری + بلاک‌شده‌ها + مرخصی + تعطیلات + نوبت‌های موجود) باید سمت سرور باشه — فعلاً پیاده نشده.
- سیستم احراز هویت واقعی (JWT/session) وصل نیست؛ صفحه‌ی `/login` فقط UI است.
- مدل داده‌ی آرایشگر در بک‌اند آینده هم باید از اول بدون `barberType` طراحی بشه — فقط `Barber` + `BarberPermission` جدول جدا.
